# 任务 2.4 规划：扩展序列化场景并复核优化收益

## 背景与目标

导师评审要求性能测试不能局限于单一数据形态，至少应覆盖中英文字符和大对象数组。
现有 JMH 已覆盖普通小对象、100 元素英文对象图和自定义序列化，但没有中文载荷和
大对象数组。本轮只扩展测试与证据，不改变已经评审通过的 JDK 实现；核心目标仍是
在保持 Java Object Serialization 格式、对象图语义和公开 API 不变的前提下，验证
`ObjectOutputStream` 优化在更广泛场景中的性能表现。

## 修改前基准与正确性

- 使用未优化提交 `3dfb920595202df2dfa5b9f5b6c3b124cf32aabf` 的 release JDK；
- 先运行 `java/io/Serializable`、`java/io/ObjectInputStream`、
  `java/io/ObjectStreamClass`，预期 160/160 通过；
- 以任务 2.1 的 9 项正式 JMH JSON 作为原有三类场景的修改前性能基线；
- 扩展 JMH 后，先在同一未优化 JDK 上采集新增场景基线，再测试优化 JDK。

## JMH 场景设计

保留 `SMALL`、`GRAPH`、`CUSTOM` 的名称和构造逻辑，保证与历史结果可比；新增：

1. `SMALL_CHINESE`：字段结构与 `SMALL` 相同，字符串改为中文；
2. `GRAPH_CHINESE`：与 `GRAPH` 相同的 100 元素对象图，名称和成员名使用中文；
3. `LARGE_OBJECT_ARRAY`：4096 个普通对象组成的数组，名称交替使用中英文，覆盖大数组、
   重复默认字段写入和两类字符编码。

每个载荷继续测量 `serialize`、`deserialize`、`roundTrip`，使用 AverageTime、单线程、
3 forks、5 次预热、5 次测量和 GC profiler。`@Setup` 必须对反序列化结果进行内容级校验，
避免只检查类型而漏掉字段或数组内容错误。

## 风险评审

| 风险 | 控制措施 |
|---|---|
| 改名导致旧结果失去可比性 | 原三类场景名称及构造保持不变，只追加参数 |
| 大数组使单轮耗时过长 | 规模固定为 4096，先 smoke 再跑正式配置 |
| 中文与英文对象结构不同 | 中文场景只替换字符串内容，节点数和字段结构一致 |
| 只验证返回类型导致功能回归漏检 | setup 中按场景校验全部标量、集合和数组内容 |
| 基准产物与 JDK 提交不匹配 | 沿用 environment schema 2、JDK 镜像哈希和 clean-worktree 检查 |

## 验收标准

- 未优化版本序列化专项 jtreg 160/160 通过；
- 最终优化版本含目标测试的序列化专项 jtreg 161/161 通过；
- JMH 18 个组合（3 操作 × 6 载荷）全部执行成功，且 setup 内容校验通过；
- 原有三类场景没有因测试代码调整而失去历史可比性；
- 分别报告各写路径耗时与 `gc.alloc.rate.norm`，不得用单一场景概括全部收益；
- 任一场景出现超出置信区间或稳定重复的回退时，不宣称总体性能提升，需继续定位或回退实现。
