# 任务 2.3 规划：JMH 对比与第二轮序列化优化

## 目标

以任务 2.1 的 Kona release 基线和相同 JMH 程序为对照，测量任务 2.2 提交
`122f6b52a`。Codex 根据时间与分配指标定位仍有改进空间的路径，完成后续 Kona 源码改进、
正确性回归和相同参数的完整复测。最终正式基线与结果自然扩展为 18 项，覆盖中英文字符、
普通对象图、4096 元素对象数组和自定义序列化，不把广泛性验证拆成额外任务。

## 实验约束

- 使用同一台 MacBook Air、同一 JMH 1.37 程序和数据模型；
- 使用 release/product JDK，3 forks、5 次预热、5 次测量，每次 1 秒；
- 同时记录 AverageTime 和 `gc.alloc.rate.norm`；
- 每轮 Kona 工作树必须 clean，并在环境文件中记录准确提交；
- 当前正式基线和最终 JSON、schema 2 环境文件与 SHA-256 校验和进入 `results/`；
- 第二轮源码必须先通过新增目标测试和完整序列化 jtreg，才能解释性能数字；
- 不用置信区间重叠的耗时结果宣称确定性加速，分配量变化单独报告。
- 中文与英文对象图保持相同节点数和字段结构；大对象数组交替包含中英文名称；
- JMH setup 对每类载荷做字段、集合和数组的内容级往返校验。

## 执行阶段

1. **Round 1：测量 2.2 实现**
   - 输入提交：`122f6b52a`；
   - 输出目录：`results/task-2.3-round1/`；
   - 使用当时的 9 项矩阵运行 `serialize`、`deserialize`、`roundTrip`，作为实现迭代证据。
2. **Codex 差异分析**
   - 与 `results/task-2.1-baseline/jmh-result.json` 按 benchmark/参数精确配对；
   - 计算绝对变化、百分比和加速比；
   - 检查收益是否集中于对象图、是否只影响写路径、浅层对象是否出现额外固定分配。
3. **进一步改进（保留中间轮次）**
   - 只修改由 Round 1 数据支持的热点；
   - 保持字段快照、递归隔离、异常清理及 wire format 不变；
   - 增补或调整 jtreg 覆盖，再构建 release 镜像并跑完整 163 项测试。
4. **最终复测**
   - 输出目录：`results/task-2.3-final/`；
   - 将正式 JMH 扩充到 6 类载荷、3 条路径共 18 项，并同步重测 2.1 基线；
   - 使用与 Round 1 相同的 forks、预热、测量和 GC profiler 参数；
   - 同时比较 2.1 基线、2.3 历史候选与最终实现，并对异常耗时执行反向顺序复测。

实际执行中，Codex 为避免用一次偶然试跑决定实现，额外保留了 Round 2（双字段）与
Round 3（惰性状态）两组完整历史结果；两者分别暴露实例大小和热路径状态判断问题，最终
收敛到“根层不缓存、只缓存嵌套层”的方案。评审后的最终提交
`0c13d1af7` 还会在顶层写入结束时释放嵌套缓存，避免长生命周期对象流保留历史最大容量。

## 验收标准

- 当前归档正式基线和最终结果均包含 JSON、schema 2 环境文件、README 和 SHA-256 校验和；
- 反向顺序聚焦复测的原始 JSON 与校验和同样进入 `results/`；
- 结果校验脚本通过，报告数字与 JSON 一致；
- 第二轮 Kona 代码和测试形成独立提交并推送到个人 fork；
- 完整序列化 jtreg 无失败、错误或跳过；
- 正式 JMH 的 18 项场景全部执行成功，内容级往返校验通过；
- 报告包含 Codex 输入、分析过程、负面或不显著结果以及最终结论。
