# 任务 2.2 规划：使用 GPT-5.6 优化 Java 序列化

## 目标与约束

在不改变 Java Object Serialization wire format、对象图语义和公开 API 的前提下，减少
默认序列化路径的临时对象分配。正确性以任务 2.1 的 160 项 jtreg 测试及新增目标测试为
准；性能验证继续使用同一套 JMH 程序、release/product 构建和参数。

Kona 主工作树已有与本任务无关的 HotSpot `memset` 告警修正。为避免覆盖或误提交这些
用户修改，2.2 在独立工作树 `/Users/rayovac9/TencentKona-25-task-2.2` 和分支
`codex/task-2.2-serialization` 上实现。

## GPT-5.6 分析

2.1 的分配结果显示 `GRAPH serialize` 为 18,664 B/op，明显高于 `SMALL serialize` 的
6,624 B/op。检查 `ObjectOutputStream.defaultWriteFields` 后发现：每序列化一个含引用字段
的普通对象，该方法都会创建一个新的 `Object[]`，先快照全部引用字段，再递归写出。
100 元素对象图会反复经过该路径，因此这些短命数组是明确且可消除的分配来源。

评估过的方案：

| 方案 | 收益 | 风险 | 结论 |
|---|---|---|---|
| 逐字段读取并立即写出 | 完全消除暂存数组 | 递归写早期字段时可能修改后续字段，破坏原有“先快照、后写出”语义 | 放弃 |
| 全流共享一个数组 | 实现简单 | 递归序列化会覆盖外层尚未写完的字段 | 放弃 |
| 按递归深度复用数组 | 同一深度的顺序对象复用缓冲区，同时保留每层字段快照 | 必须处理数组扩容、异常清理和引用滞留 | 采用 |

## 实现方案

1. 在 `ObjectOutputStream` 中维护按 `depth` 索引的 `Object[][]` 暂存区。
2. `defaultWriteFields` 按需创建或扩容当前深度的 `Object[]`，不缩小已有数组。
3. 字段索引始终使用描述符的 `numObjFields`，不能使用可能更大的缓存数组长度。
4. 在 `finally` 中将本次使用的区间清空，避免缓存延长被序列化对象的生命周期。
5. 保持先调用 `getObjFieldValues` 完成快照、再逐项递归写出的原有顺序。

## 测试方案

1. 新增目标 jtreg：早期字段的自定义 `writeObject` 会修改同一对象的后续字段，验证流中
   仍保存递归开始前的字段快照。
2. 构建 Kona JDK 25 release 镜像。
3. 运行新增目标 jtreg。
4. 运行与 2.1 相同的三个目录，共 160 项序列化 jtreg；新增测试后预期总数为 161。
5. 使用相同 JMH 程序先做短时 A/B 试跑，确认 `GRAPH serialize` 分配量下降且没有明显
   性能回退。正式完整 JMH 对比和下一轮改进属于任务 2.3。

## 验收标准

- 新增目标测试和完整序列化 jtreg 全部通过；
- 输出字节流可由原实现读取，原实现产生的基准数据也可由优化实现读取；
